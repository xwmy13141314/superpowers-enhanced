# Brainstorming - 设计优先技能

**当以下情况时使用此 Skill**：
- 用户要求创建新功能、组件或系统
- 需要修改现有代码的行为或架构
- 用户提出一个想法但需求不清晰
- 在编写任何实现代码之前

## 核心原则

**硬性规则：在呈现设计并获得用户批准之前，绝对不要编写任何实现代码。**

无论项目看起来多么简单——待办列表、单函数工具、配置更改——都必须经过设计流程。"简单"项目往往因为未检验的假设导致最多的返工。

## 触发条件

当用户表达以下意图时自动触发：
- "帮我创建一个..."
- "我想实现..."
- "添加一个...功能"
- "修改...的行为"
- 任何涉及创建或修改代码的请求

## 流程

### 1. 探索项目上下文

首先检查当前项目状态：
- 读取相关文件、文档
- 了解现有架构和模式
- 检查最近的提交历史（如果适用）

### 2. 提出澄清问题

**一次只问一个问题**，不要一次性抛出多个问题。

关注理解：
- 目的：这个功能解决什么问题？
- 约束：有什么技术或业务限制？
- 成功标准：怎么算完成？

优先使用选择题（A/B/C），必要时使用开放式问题。

### 3. 提出 2-3 种方案

提供不同的实现方法，包括：
- 每种方案的权衡
- 你的推荐及理由
- 复杂度、可维护性、扩展性对比

### 4. 呈现设计

在用户批准方案后，呈现详细设计：
- 架构概述
- 组件划分
- 数据流
- 错误处理
- 测试策略

**设计原则**：
- 每个单元有单一明确的目的
- 通过定义良好的接口通信
- 可独立理解和测试
- 文件保持专注，避免过大

### 5. 创建设计文档

将批准的设计保存到：
```
docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md
```

使用 `feishu_create_doc` 创建飞书云文档（如果在飞书环境中）。

### 6. 设计自检

在继续之前，检查设计文档：
- 是否有 "TBD"、"TODO" 等占位符？→ 修复
- 各部分是否有矛盾？→ 修复
- 范围是否过于宽泛？→ 分解
- 是否有歧义的需求？→ 明确化

### 7. 用户评审

请求用户评审设计文档：
> "设计文档已创建。请评审并告知是否需要修改，然后我们再开始编写实施计划。"

等待用户批准后再继续。

### 8. 过渡到实施

用户批准后，调用 `writing-plans` 技能创建实施计划。

## 与 OpenClaw 集成

### 使用子代理进行头脑风暴

对于复杂项目，可以 spawn 一个子代理专门负责头脑风暴：

```
sessions_spawn(
  runtime="subagent",
  task="进行头脑风暴，遵循 design-first 流程",
  mode="session"
)
```

### 使用 Canvas 进行视觉展示

当涉及 UI/视觉问题时，可以使用 `canvas` 工具展示：
- 原型图
- 架构图
- 布局对比

## 反模式警示

**永远不要说**：
- "这个太简单了，不需要设计"
- "我先写代码，稍后再补设计"
- "我理解你要什么了"（没有经过澄清问题）

**正确做法**：
- 每个项目都经过设计流程
- 设计可以简短，但必须存在
- 通过问题验证理解

## 输出格式

在飞书环境中，使用结构化消息呈现设计：

```markdown
## 设计方案

### 目标
[一句话描述]

### 推荐方案
[方案描述 + 理由]

### 备选方案
- 方案 B: [描述 + 权衡]
- 方案 C: [描述 + 权衡]

### 架构
[组件图/描述]

### 关键决策
- 决策 1: [说明]
- 决策 2: [说明]

---
请确认以上设计是否符合你的预期？需要调整吗？
```
