# Requirement Analysis - 需求分析技能

**当以下情况时使用此 Skill**：

- 收集到用户需求，需要梳理和分析
- 用户说"帮我整理一下需求"、"需求太多了"
- 需要编写用户故事、验收标准
- 需要确定需求优先级
- 在产品设计或开发之前

## 核心原则

**清晰明确的需求 > 模糊笼统的想法**

需求分析是产品开发的基础。模糊的需求会导致返工和浪费。清晰、明确、可验证的需求是成功交付的前提。

## 工作流程

### 阶段 1: 需求收集

#### 1.1 需求来源识别

**常见需求来源：**

- **用户反馈** - 客服、问卷、评论
- **数据分析** - 用户行为数据、流失数据
- **市场调研** - 市场机会、竞品分析
- **利益相关者** - 业务方、管理层、运营
- **技术驱动** - 技术升级、架构优化

#### 1.2 需求收集方法

**定性方法：**

- **用户访谈** - 深度了解用户需求
  - 一对一访谈（30-60 分钟）
  - 用户观察（现场看用户使用产品）
  - 焦点小组（6-8 人小组讨论）

- **问卷调查** - 大规模需求收集
  - 在线问卷（问卷星、Google Forms）
  - 问卷设计（10-15 个问题）
  - 样本量（至少 100 份）

**定量方法：**

- **数据分析** - 从数据中发现需求
  - 用户行为分析（哪些功能用得多）
  - 漏斗分析（哪里流失）
  - 留存分析（为什么流失）

- **A/B 测试** - 验证需求假设
  - 对比不同方案
  - 测量用户反应

### 阶段 2: 需求梳理

#### 2.1 需求分类

**按 MoSCoW 方法分类：**

- **Must Have（必须有）** - 核心功能，没有无法上线
- **Should Have（应该有）** - 重要但非紧急
- **Could Have（可以有）** - 有了更好，没有也行
- **Won't Have（不会有）** - 明确不做

**按类型分类：**

- **功能需求** - 产品必须做什么
- **非功能需求** - 性能、安全、可用性
- **约束条件** - 技术约束、时间约束、资源约束
- **业务规则** - 业务逻辑、计算规则

#### 2.2 需求去重

**识别重复需求：**

- 相似需求合并
- 冲突需求标记
- 依赖关系标注

### 阶段 3: 用户故事编写

#### 3.1 用户故事模板

**标准格式：**

```
作为 [角色]
我想要 [功能]
以便 [价值]
```

**示例：**

```
作为 内容创作者
我想要 AI 辅助写作
以便 提高写作效率
```

#### 3.2 用户故事 INVEST 原则

**好的用户故事应该：**

- **I (Independent)** - 独立的，不依赖其他故事
- **N (Negotiable)** - 可协商的，不是固定需求
- **V (Valuable)** - 有价值的，对用户有价值
- **E (Estimable)** - 可估算的，能评估工作量
- **S (Small)** - 小的，能在 1-2 周完成
- **T (Testable)** - 可测试的，有明确的验收标准

#### 3.3 用户故事拆分

**拆分方法：**

- **按用户角色** - 不同角色有不同需求
- **按使用场景** - 不同场景有不同需求
- **按功能模块** - 大功能拆成小功能
- **按数据类型** - 不同数据类型有不同处理逻辑

### 阶段 4: 验收标准定义

#### 4.1 验收标准格式

**Given-When-Then 格式：**

```
Given [前置条件]
When [触发动作]
Then [预期结果]
```

**示例：**

```
Feature: AI 辅助写作

Scenario: 用户使用 AI 生成内容
  Given 用户已登录
  And 用户在写作编辑器页面
  When 用户输入提示词"写一篇关于 AI 的文章"
  And 点击"生成"按钮
  Then 系统应该在 5 秒内生成一篇 500 字的文章
  And 文章应该相关且连贯
  And 用户可以编辑和保存
```

#### 4.2 验收标准检查清单

**完整性检查：**

- [ ] 覆盖所有用户场景
- [ ] 包含正常流程和异常流程
- [ ] 定义了明确的性能指标
- [ ] 定义了明确的边界条件
- [ ] 可测试、可验证

### 阶段 5: 需求优先级排序

#### 5.1 优先级评估方法

**RICE 评分法：**

```
RICE = (Reach × Impact × Confidence) / Effort
```

- **Reach（触达）** - 多少用户会用到（1-10 分）
- **Impact（影响）** - 对用户的影响多大（0.25-3 分）
- **Confidence（信心）** - 对评估的信心（50%-100%）
- **Effort（工作量）** - 需要多少工作量（人月）

**示例：**

| 需求 | Reach | Impact | Confidence | Effort | RICE 分 | 优先级 |
|------|--------|--------|------------|--------|---------|--------|
| AI 写作 | 8 | 3 | 90% | 2 | 10.8 | P0 |
| 模板库 | 6 | 2 | 80% | 1 | 9.6 | P1 |
| 协作编辑 | 4 | 2 | 70% | 3 | 1.9 | P2 |

#### 5.2 依赖关系分析

**识别依赖关系：**

- **功能依赖** - 功能 A 依赖功能 B
- **数据依赖** - 数据 A 依赖数据 B
- **技术依赖** - 技术 A 依赖技术 B

**绘制依赖图：**

```
需求 A ────────> 需求 B
                   │
需求 C ──────────────┘
```

### 阶段 6: 需求文档

**创建飞书文档，包含：**

1. **需求概述** - 背景和目标
2. **用户角色** - 目标用户定义
3. **用户故事** - 完整的用户故事列表
4. **验收标准** - 每个故事的验收标准
5. **优先级** - MoSCoW 或 RICE 评分
6. **依赖关系** - 需求之间的依赖
7. **非功能需求** - 性能、安全、可用性
8. **约束条件** - 技术、时间、资源约束


## 质量标准

### 需求质量检查

完成需求分析后，必须验证：

- [ ] 需求完整性（覆盖所有用户场景）
- [ ] 需求明确性（无歧义）
- [ ] 需求可测试性（有验收标准）
- [ ] 需求可实现性（技术可行）
- [ ] 优先级合理性（RICE 评分）
- [ ] 依赖关系清晰

### 常见错误

❌ **避免：**
- 需求过于笼统、模糊
- 只有功能需求，没有非功能需求
- 没有验收标准
- 优先级混乱
- 忽视约束条件

✅ **应该：**
- 需求清晰、明确
- 功能 + 非功能需求
- 每个需求有验收标准
- RICE 评分排序
- 明确约束条件
